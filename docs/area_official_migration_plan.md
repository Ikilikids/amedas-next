# 気象庁公式細分区域ベースのエリア分割 移行計画書

## 1. 目的と課題意識
- **現状の課題**: 現在の県内エリア分割（2〜4分割）はAIが生成したものであり、「なぜこの県が2分割で、他が3分割なのか」「境界線がどこか」という客観的な根拠が薄い。
- **目標**: 気象庁が告示している**公式の「気象警報・注意報の細分区域」**に完全準拠し、客観的・機械的に全アメダスをエリアに割り振る仕組みを構築する。

---

## 2. 採用する公式区分のレベル（一次区分 vs 二次区分）

気象庁の公式区分には2段階あります。どちらを基本とするかで粒度が決まります。

| 区分レベル | 全国の数 | 例（東京都） | 特徴・所感 |
| :--- | :--- | :--- | :--- |
| **一次細分区域** | 約 140 区分 （1県あたり 1〜4 程度） | ・東京地方<br>・伊豆諸島北部<br>・伊豆諸島南部<br>・小笠原諸島 | 大枠のまとまりとして非常に見やすい。<br>※ただし埼玉・千葉・神奈川などは県全体で「1区分（南部/北部などの分割なし）」になってしまう県がある。 |
| **二次細分区域** | 約 370 区分 （1県あたり 3〜8 程度） | ・東京23区<br>・多摩北部<br>・多摩南部<br>・多摩西部 など | **推奨**。天気予報や警報でおなじみの「北部・南部・秩父」などの単位。<br>市町村と1対1で対応し、気候解説記事のボリュームとして最も適切。 |

> **推奨方針**: 各都道府県の解説ページ（`areaSections`）には、天気予報や警報発表の単位として広く馴染み深い**「二次細分区域」**（警報発表区域）を採用する。

---

## 3. 実装アーキテクチャ

### (1) 市区町村 → 公式区域マッピングテーブル（JSON）の作成
気象庁の公表データ（[警報・注意報の発表区域等一覧](https://www.jma.go.jp/jma/kishou/know/saibun/)）から、市町村名をキーにした辞書データを構築します。

```json
// src/data/official_area_mapping.json (イメージ)
{
  "43": { // 埼玉県
    "熊谷市": "saitama_hokubu",
    "深谷市": "saitama_hokubu",
    "さいたま市": "saitama_nanbu",
    "秩父市": "saitama_chichibu"
  },
  "44": { // 東京都
    "千代田区": "tokyo_23ku",
    "八王子市": "tokyo_tama_nanbu",
    "西多摩郡奥多摩町": "tokyo_tama_seibu"
  }
}
```

### (2) アメダスの自動所属判定
`stations.json` の各地点は `pref` と `city` を持っているため、以下のコードで100%自動で所属エリアが特定できます。

```typescript
function getStationArea(station: RawStationData): string {
  const prefMapping = officialAreaMapping[station.pref];
  if (!prefMapping) return "other";
  return prefMapping[station.city] || "unknown";
}
```

## 4. 移行手順（ロードマップ）

### フェーズ 1: 公式区域マスターの整備
1. 気象庁の公開資料から、全1,741市区町村の「都道府県コード」「一次細分」「二次細分名」を収集してJSON化。
2. 都道府県ごとの公式二次細分区域リスト（キー・名称）を定義。

### フェーズ 2: 既存の `src/data/area/` の統合・再編
1. 現在の `src/data/area/[prefKey]/` 内のファイルを、気象庁の公式二次細分区域に対応する構成にマイグレーション。
   - 例（埼玉県）: `hokubu`（北部）、`nanbu`（南部）、`chichibu`（秩父）
2. 各エリアの解説文・キャッチフレーズ・代表雨温図（`uonzuList`）を公式区域単位にリフレッシュ。

### フェーズ 3: ページ表示への反映
1. `getAreasForPref(prefKey)` が公式区域順にデータを返すように統一。
2. 各観測所の詳細ページ（`station/[id].tsx`）などでも、「所属地域: 埼玉県北部」のように公式エリア名を表示可能にする。

## 5. 将来の拡張：標高フィルター（山岳エリアの切り出し）

もし「公式区分だけだと静岡市や日光市で山と平地が混ざる」という問題に対処したくなった場合、**この基盤の上に1行の例外ルールを乗せるだけで実現可能**です。

```typescript
function getStationAreaWithElevation(station: RawStationData): string {
  // 例外ルール：標高500m以上（長野・山梨等の中央高地県を除く）は「山岳・高原部」として自動分岐
  if (station.height >= 500 && !["48", "49"].includes(station.pref)) {
    return `${station.pref}_mountain`; // 例: 静岡中部山岳部、栃木北部山岳部
  }
  // 基本は公式二次細分
  return getStationArea(station);
}
```
このように設計しておけば、まずは完全公式で運用し、後から気になった時点で標高ルールをスイッチオンできます。
